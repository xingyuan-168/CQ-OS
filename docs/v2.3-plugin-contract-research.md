# V2.3 CQ Plugin 契约与维护模式调研

## 三层边界

- `package.json`：复用 npm 的 id、SemVer、exports、依赖和锁文件，作为分发信封；
- `cq-plugin.yml`：CQ 唯一新增的薄语义契约，声明兼容范围、权限、迁移、生命周期和安全自评估；
- `agent.cordis.yml` rows：复用 DSH loader 和真实 plugin row，负责运行时组合与 `standingKeyFor`。

CQ Plugin 不能冒充 DSH Plugin，也不创建第二套 preset 解析器。

## 最小契约字段

`schemaVersion`、`id`、`name`、`version`、`license`、`engines`、`depends`、`contributes`、`permissions`、`migration`、`lifecycle`、`security`。

硬规则：manifest.version 必须等于 package.json.version；SemVer engines 不满足即拒装；row id 冲突、包不可解析、host-plane row、服务行脱离 isolate realm、`standingKeyFor` 失败均 fail-closed。permissions 只是声明，真正执行仍依赖 DSH guard/pre-execute/approval/sandboxPolicy。

## 开源复用结论

- npm：复用 package.json、SemVer、exports 和 lockfile；
- VS Code：借鉴 contributes、engines 和 extensionDependencies；
- Backstage：借鉴领域边界与独立版本；不建设在线市场；
- Jenkins/Home Assistant：借鉴增强 core、manifest 和生命周期；
- MCP：借鉴 capability 声明，不引入传输层；
- DSH：复用 loader、preset generation、copy/resolve/standingKeyFor。

## 维护模式

日常 `cq-os` 永不挂载 `tool-cordis`。维护能力使用独立用户预设 `cq-os-maint`，由人类显式开启；普通角色和日常 Core 无法自行进入。维护修改先进入工作区 `preset/`、Git review，再通过 copy/resolve/standingKeyFor 部署；维护会话完成后卸载。

## 必须先做的 PoC

1. 消费型 plugin row 可合并并通过 standingKeyFor；
2. isolate 服务行可挂载且不冲突；
3. 松散服务行是否被 runtime 拒绝；若不拒绝，增加显式契约校验器；
4. host-plane row 被拒绝；
5. version/engines/id 冲突 fail-closed；
6. 日常 cq-os 无 cordis 工具，维护预设才有。
