# V2.2 模型路由开源调研与方案决策

## 结论

首期先复用 DSH 原生 per-agent `provider/model`、`agent/request` 选择、带内 provenance 和同 provider retry，不引入模型代理。只有验收明确需要跨 provider failover、虚拟模型名、预算或成本聚合时，才组合自托管 LiteLLM 作为 OpenAI-compatible provider/baseURL 后端。OpenRouter 仅作为可选上游兜底；Semantic Router/RouteLLM 作为后续路由前置；LangChain/LangGraph 是编排框架，与 DSH Agent 编排层重叠，不作为 provider 适配层。

## 候选判定

| 方案 | 判定 | 原因 |
|---|---|---|
| DSH provider/model + retry | 复用 | 当前 OpenAI-compatible provider/baseURL 能力，集成成本最低 |
| LiteLLM | 首选二开/组合 | MIT、自托管、OpenAI-compatible、fallback、预算、成本和日志 |
| OpenRouter | 可选上游 | 接入简单但闭源 SaaS，不作为主方案 |
| Portkey | 暂缓 | 网关能力强，但完整观测和治理有商业依赖 |
| Semantic Router | 后续组合 | 语义路由库，不直接提供 DSH provider endpoint |
| RouteLLM | 后续组合 | 可做成本质量路由，但当前范围窄，先不叠加复杂度 |
| LangChain/LangGraph | 放弃 provider 层 | 编排框架，和 DSH Agent Loop 语义重叠 |

## 实际请求模型验收

必须做三层对账：

1. DSH 请求层：记录 requested provider/model；
2. LiteLLM 响应和网关日志：读取 served model、provider、cost；
3. 确定性探测：固定 prompt、响应字段和故障注入验证 fallback，不使用“询问模型身份”作为唯一证据。

记录摘要格式：`requested`、`served`、`gateway`、`cost`、`fallback`、`routeReason`。不保存完整请求/响应日志到 `.cq/`。

## 最小 PoC

使用本地 LiteLLM Docker 或 Python 环境，不修改 DSH 默认设置：

- 配置一个虚拟模型映射到真实 provider；
- 验证 `/v1/models` 和一次 chat completion；
- 对账响应 `model` 与网关 spend/log；
- 故障注入首选 upstream，验证 fallback；
- 记录实际 served provider/model。

只有 PoC 通过后，才增加 CQ 可选 provider 配置和路由 Skill。

参考：[LiteLLM](https://github.com/BerriAI/litellm)、[OpenRouter routing](https://openrouter.ai/docs/features/provider-routing)、[Semantic Router](https://github.com/aurelio-labs/semantic-router)、[RouteLLM](https://github.com/lm-sys/RouteLLM)。
