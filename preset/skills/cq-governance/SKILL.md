# CQ Governance

## V0.1 定位

CQ OS V0.1 是强流程提示加可验证行为，不是不可绕过的策略引擎。工具级 `toolFilter` 是硬限制；资源、路径和职责限制依赖 Core persona、Skill 和角色纪律。路径级 RBAC 和硬治理拦截属于 B2 CQ Governance Plugin。

## 铁律

- 新项目必须经过需求分析、开源调研、技术决策、设计、开发。
- 没有设计确认，不得委派 Developer 或修改实现代码。
- CQ OS 永久修改必须先改工作区 Git 仓库的 `preset/`，不能直接编辑 DSH 用户预设部署目录。
- Git 不可用时初始化阻塞，不得使用手工快照或 v1/v2/v3 复制目录。
- Developer 不修改治理规则、删除核心数据或修改生产环境。V0.1 依赖 persona 约束，后续由 B2 强制执行。

## 确认门

架构重大调整、数据库重大修改、大规模重构、生产发布、高风险操作必须回到 Core 请求人工确认。前端项目完成 UX/UI 后，workflow 返回 Core；Core 单独调用 `ask_user_question`，等待回答后再启动开发。

## 失败恢复

任何恢复动作按顺序执行，并写入 `.cq/` 提炼记忆：

1. 工具/API 短暂错误 → 有限次数自动重试。
2. 同一角色连续失败 → Core 重新委派或调整任务、拆分范围。
3. 模型表现异常 → 后续支持换模型（当前 V1 记录为待办）。
4. 代码导致测试失败且无法恢复 → Git 回滚到安全点。
5. 涉及破坏性操作或多次恢复失败 → 请求人工介入。
6. 记录恢复动作、原因和结果到 `.cq/` 相关记忆文件，关联 commit。

禁止无记录地绕过或吞掉失败。

## 工具循环熔断（LOOP_BREAKER）

1. 相同工具 + 相同参数：最多执行 1 次，禁止重复。
2. 相同目标 + 等价参数：最多 2 次，第二次必须是真正换方案的重试。
3. 连续多次工具调用没有新增信息：判定 `LOOP_BREAKER_TRIGGERED`，立即停止工具调用。
4. 触发后：BLOCKED → 总结已知事实 → 根因分析 → 换方案 → 必要时 Human Intervention。

禁止无新信息的重复 read/grep/open。

## 质量与安全

按风险选择单元、集成、API、UI、性能和安全测试。密钥不得写入仓库，保护环境变量，执行依赖漏洞检查。Review 先于交付。

## 工作区边界

角色读取以当前工作区为主。确需参考工作区外内容（如兄弟项目、外部档案）时，角色须先经 Core 请示，Core 允许后才可读取；角色不得擅自扩大读取范围。工作区外的写入一律禁止（由文件沙箱按 `workspace-write` 策略约束）。

## 澄清链路

角色禁止直接向用户提问（`ask_user_question` 为 Core 专属）。角色如有澄清、未决问题或歧义，经 `report` 向 Core 上报；由 Core 统一触发 `ask_user_question` 与用户确认，再把结果回传给角色。

## 已知无法从角色侧验证的能力项

以下能力项在委派会话模式下，角色只能依据运行时快照声明、无法从角色侧实测，属明确的验收边界（不得重复探测）：

- 审批栈实际行为（会话声明“审批提示禁用”，未触发真实审批流程）
- PowerShell 语言模式 / ConstrAedLanguage 与 .NET 调用限制（仅 `echo` 类探针，或被 deny 无 shell）
- 工作区**外**写入是否被阻止（`workspace-write` 只承诺工作区内写；角色侧不主动越界写）
- `skill` 工具加载后的实际效果（仅确认技能目录可见，未加载内容）
- 后台任务工具（`job_*`）实际行为（自检未启动后台任务）
- 无法枚举“未暴露给本角色的工具”（只能枚举运行时可见项）

这些项仅在 V1 验收需要时由 Core 侧面/宿主侧核验，不属于角色自检能闭环的范围。
